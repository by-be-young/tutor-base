## 3. 维护规则

1. **一次行为变更，多处同步**（见 [`../AGENTS.md`](../AGENTS.md)）：`CONTEXT.md`、`openapi.yaml`、`api-standards.md`、`backend-completion-matrix.md`、本文相关文档、代码与测试。
2. **需求先落 SRS**：新增能力先写 `FR-*` 与验收要点，再写故事与实现；临时试验可以只写故事，但上线前补齐 SRS。
3. **对象先落清单**：新增表或改变对象语义，先更新 `业务对象清单.md` 的标识、不变量与删除影响，再改 migration。
4. **不写实现细节到领域词表**：`CONTEXT.md` 只放词汇定义与反义词，表名、类名、接口路径放到本文或 `业务对象清单.md`。
5. **历史文档不粉饰**：状态变化时在文首加"状态/日期"说明，保留决策痕迹；不要静默改写历史结论。
6. **不复制事实**：接口字段以 `openapi.yaml` 为准，表结构以 migration 为准；本文只做索引与解释，避免三处维护同一字段清单。
7. **中文为主，代码与协议标识保留原文**（如 `articleId`、`questionKey`、`correct/partial/wrong`）。
8. **提交前检查链接**：相对链接必须可解析；新增文档在本索引登记。

## 5. 文档质量检查清单

- [ ] 新增概念已进 `CONTEXT.md`，且列出了"避免叫法"。
- [ ] 需求有编号（`FR-*`）、验收有可观察结果、故事能追溯到需求。
- [ ] 对象有标识、不变量、持久化形态与删除影响。
- [ ] 接口路径与 `openapi.yaml` 一致，错误码在 `api-standards.md` 有定义。
- [ ] 时间口径（UTC vs Asia/Shanghai）写清楚。
- [ ] 明确写出"不做什么"，避免读者误以为已支持。
- [ ] 相对链接可点击，表格无错列。
